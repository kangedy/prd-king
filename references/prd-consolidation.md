# PRD文档整合工作流

当用户说"整合成一版本完整PRD"、"全部合并成一份"、"把所有文档合成一个"时使用。

## 触发

- "整合成一版本完整PRD"
- "全部合并成一份"
- "把这些文档合成一个最终版"
- "小乔全部整合成一版本完整PRD"

## 工作流

### Step 1: 确认源文件

列出所有需要整合的源文件，确认路径和内容概要：

```bash
ls -la ~/项目目录/*.md
```

典型场景：多轮迭代后积累的多个版本PRD文件：
- V1.0（初版架构+表格列）
- V2.0（补充章节）
- V3.0（完整表单字段）
- 业务流程梳理文档

### Step 2: 委派子Agent整合

使用 delegate_task 指派产品专家子Agent执行合并：

```
delegate_task(
  goal="整合四份文档为一份完整的XX系统PRD",
  context="""你就是小乔（产品专家）。
  
源文件路径：
1. /path/to/PRD_V1.0.md — 主架构+模块表格列
2. /path/to/PRD_V2.0.md — 补充章节
3. /path/to/PRD_V3.0.md — 完整表单字段
4. /path/to/业务流程.md — 业务流程

用 read_file 读取所有源文件，然后整合为一份完整PRD，用 write_file 输出到 /path/to/PRD_完整版_FINAL.md

按以下结构组织：
1. 文档头(版本/日期/编制)
2. 系统概述与架构
3. 用户角色定义
4. 业务流程全景
5. 逐模块详述(含完整表格列和表单字段)
6. 报表中心
7. 系统管理
8. 关键数据字典
9. 交付批次建议
10. 验收标准

要求：不遗漏任何一个字段，中文输出。
""",
  toolsets=["file"]
)
```

**关键Context要点：**
- 明确告诉子Agent有哪些源文件及路径
- 指定输出文件路径
- 列出目标文档的章节结构
- 强调"不遗漏任何一个字段"
- 指定目标技能（小乔/产品专家）

### Step 3: 验证输出

子Agent完成后验证：
- 文件是否成功写入
- 行数/字节数是否合理（合并后应大于任一源文件）
- 关键章节是否存在（head验证）
- 关键字段是否完整（search_files验证）

```bash
wc -l /path/to/PRD_完整版_FINAL.md
head -20 /path/to/PRD_完整版_FINAL.md
```

### Step 4: 归档旧版本

按照文件整理规范，将旧版本移入 `7_旧版本/` 目录：

```bash
mkdir -p 7_旧版本
mv PRD_V1.0.md PRD_V2.0.md PRD_V3.0.md 7_旧版本/
```

**只保留一份最终版PRD在主目录下。**

## 本章节结构模板

整合后的PRD应包含以下章节：

| 章 | 内容 |
|:--|:-----|
| 1 | 文档头 — 版本/日期/编制/整合来源 |
| 2 | 系统概述 — 产品定位/四层架构图/技术栈+选型建议 |
| 3 | 角色定义 — 所有角色 + 权限矩阵(行=角色, 列=模块) |
| 4 | 业务流程 — 全景图 + 10核心流程 + 状态机 + 核心公式 |
| 5 | 模块详述 — 每个模块: 路径/优先级/表格列/表单字段/搜索/功能点/验收 |
| 6 | 报表中心 — 所有报表列表 + 字段 + 筛选维度 |
| 7 | 系统管理 — 用户/角色/菜单/部门/岗位/字典/参数/日志 |
| 8 | 数据字典 — 所有枚举值 |
| 9 | 交付计划 — 分期/模块/工期 |
| 10 | 验收标准 — 可测量的完成定义 |

## 🚨 致命坑：子Agent压缩陷阱

**这是PRD整合中最严重的错误模式。** 当使用 delegate_task 委派子Agent合并多份PRD时，子Agent几乎**必然**会压缩详细内容。

**典型失败模式：**
- 源V5.0 PRD有1962行，包含83字段车辆信息完整表单、50字段结算导出等详细规格
- 子Agent输出1269行，后管详细设计被压缩成"V4.0保留：83字段完整保留"一句话
- **结果：丢失了所有字段级细节**，只剩摘要骨架

**为什么会发生：** 子Agent没有"不压缩"的意识。它的自然倾向是用摘要替代细节，尤其是当它认为内容"重复"时。

**正确做法：不要委托子Agent做细节合并。** 用终端 `cat` 直接拼接文件：

```bash
cat header.md "小程序PRD.md" separator.md "后管PRD.md" > final.md
```

这保证零删减、零压缩。

## 致命坑：read_file对大文件静默失败

`read_file` 在文件超过 ~96KB 时返回 0 chars / 1 line，**不报错、不提示**。这导致基于 read_file 的文件合并产生空输出。

**症状：** read_file 报告 `content: ''` 或 `1 line`，但文件实际有几千行。

**修复：** 对 >80KB 的文件，用 `terminal cat` 代替 read_file：

```bash
wc -l /path/to/large_file.md  # 先确认行数
cat /path/to/large_file.md > /tmp/output  # 直接操作
```

## 巨型项目多源整合工作流（商业DOCX+补充MD+验收清单→VERSION B）

当用户说\"整合全部资料输出完整AI开发版PRD，100%覆盖验收清单N个功能点\"时使用。这是整合工作流中最复杂的场景：原始资料分散在商业交付版DOCX、多份补充MD、甲方验收清单Excel三者之间。

### 触发

- \"整合全部资料，输出完整AI开发版PRD (VERSION B)\"
- \"XXXXX项目全部资料整合成一版本，100%覆盖验收清单\"
- \"把XX DOCX + XX MD + XX Excel整合成一个VERSION B PRD\"

### 执行步骤

**Step 1 — 并行批量读取所有源文件**

一次性发起所有 read_file 调用，不分批等待。独立文件之间无依赖，并行读取效率最高：

```python
# 并行读取策略
batch_1 = [read_file(f) for f in supplementary_prds]  # 9份补充PRD
batch_2 = [read_file(f, offset=0, limit=200) for f in large_files]  # Excel首段
# 如需后续页：read_file(offset=200), read_file(offset=400)...
```

**典型源文件清单：**
- 原始商业版PRD (.docx, 可能100MB+) → 用 `python3 -c "from docx import Document; doc=Document(...)"` 提取标题结构
- N份补充PRD (.md, 200-500行) → 逐个 read_file 全文读取
- 甲方验收清单 (.xlsx, 4000+行) → 分批 read_file(offset=0/200/400...) 提取模块层次
- 政策/管理办法 (.docx) → 提取关键参数更新

**Step 2 — 以验收清单为\"主清单\"建立模块→功能点映射**

Excel验收清单是甲方的权威覆盖标准。用它作为主索引，逐行对标所有PRD来源：

```python
# 从Excel行提取模块层次
for line in checklist_lines:
    parts = line.split('\t')
    subsystem = parts[1]   # 子系统
    l1, l2, l3 = parts[2:5]  # 一级/二级/三级模块
    fp_name = parts[5]     # 功能点名称
    fp_type = parts[6]     # ILF/EI/EQ/EO/EIF

# 构建模块→功能点计数→验收清单行号区间的映射
modules[key] = {"count": N, "rows": "A-B"}
```

**Step 3 — 交叉验证：双向对标**

```
Excel → PRD: 逐行检查Excel功能点是否在PRD中有对应描述
  ✅ 存在 → 标注来源（如【DOCX原文】【service_strategy_center_prd.md】）
  🔴 不存在 → 标记【缺失·需补充】
  ⚠️ 非本期 → 标注排除原因

PRD → Excel: 逐项检查PRD模块功能点是否在Excel中有对应行
  ✅ 存在 → 标注交付清单引用
  ✅ 不存在 → 保留并标记【PRD原始】（Excel未列但PRD已有，如AI能力模块）
```

**Step 4 — 按10章VERSION B标准输出**

| 章节 | 整合策略 |
|------|---------|
| Ch1 | 从原始PRD或项目背景提取设计系统Token |
| Ch2 | 以验收清单模块层次为骨架，构建4子系统树形导航 |
| Ch3 | 从原始PRD/DOCX提取核心流程 + 补充PRD的详细流程 |
| Ch4 | 提取权限矩阵+数据流向，不写微服务/DB等无关细节 |
| Ch5 | 每个页面 unique data-page + 布局类型 + 依赖实体 + 来源标注 |
| Ch6 | 模块→功能点总数映射表（引验收清单编号区间）+ 2-3个逐按钮示例 |
| Ch7 | 跨系统核心实体（8-10个），各模块详细字段参见补充PRD |
| Ch8 | 跨系统Mock数据（使用真实业务场景数据，非\"测试数据\"） |
| Ch9 | 从各补充PRD提取+补充通用边界条件 |
| Ch10 | 覆盖率矩阵 + 补充PRD索引表 + 12项门禁 |

**Step 5 — 覆盖率自检**

输出前运行：
```bash
# 行数检查
wc -l output.md  # 应显著 > 任一源文件

# 章节完整性
python3 scripts/validate-prd.py output.md  # 必须 ≥80%

# 引用完整性
grep -c "补充PRD" output.md  # 确认所有源文件都被引用
```

### 致命坑：不要用子Agent做这种整合

**这个工作流必须由主Agent亲自完成**，原因：
- 子Agent看不到/读不全 >80KB 的大文件（read_file静默截断）
- 子Agent会压缩字段级规格为摘要（\"83字段完整保留\"替代83字段逐字段表）
- 子Agent做不了交叉验证（看不到全部源文件）
- 子Agent的输出格式不可控（可能跳过10章结构）

**正确做法：主Agent逐章节自行输出，用 write_file 一次性写入整个文件。**

### 源文件标注规范

在PRD的每个模块/功能点处标注来源：
- `【DOCX原文·完整】` — 来自原始商业PRD，内容完整
- `【supplementary_prd_name.md · 100%】` — 来自对应补充PRD
- `【新增整合】` — 主Agent根据多源信息新编写的整合内容
- `【非本期范围·待甲方确认】` — 验收清单中有但当前不在范围的模块

### 真实案例参考

某省级交通集团客户中心项目（本session）：
- 源文件：1份118MB商业DOCX + 9份补充MD + 1份Excel(4,190行)
- 输出：889行VERSION B PRD，100% P0验证通过
- 覆盖：4,179个功能点，4子系统60模块，100%覆盖率

## Shell拼接技术：sed/tail精确提取

当多份源文件各自有独立的 `# 标题` 和文档头（版本/日期/编制）时，不能简单 `cat` 全部文件——会导致重复标题和混乱的层级。需要使用 sed 或 tail 跳过冗余内容：

### 模式1：跳过首行标题后全部追加 (`tail -n +2`)

源文件结构简单，只有首行 `# 标题` 是冗余的：

```bash
# 跳过源文件首行标题，其余全部追加
tail -n +2 source_file.md >> merged.md
```

### 模式2：从指定锚点开始提取 (`sed -n`)

源文件前半部分是文档元信息（版本/日期/FPA说明等），需要从特定锚点开始提取：

```bash
# 从 "## 模块总览" 行开始提取，跳过前置文档头
sed -n '/^## 模块总览/,$ p' source_file.md >> merged.md
```

### 模式3：跳过整个文档头部到第一个 `##` 标题

```bash
# 从第一个 ## 二级标题开始提取
sed -n '/^## /,$ p' source_file.md >> merged.md
```

### 完整拼接脚本模板

```bash
BASE="/path/to/source"
OUT="$BASE/完整版PRD.md"

# 1. write_file 写入文档头 + 总目录
# 2. 逐编追加：

echo "" >> "$OUT"
echo "---" >> "$OUT"
echo "" >> "$OUT"
echo "# 第X编：XX模块" >> "$OUT"
echo "" >> "$OUT"
echo "> **来源文件**: xx.md" >> "$OUT"
echo "> **功能点**: N个" >> "$OUT"
echo "" >> "$OUT"

# 根据源文件结构选择合适的提取方式
sed -n '/^## 模块总览/,$ p' "$BASE/source.md" >> "$OUT"

# 或
tail -n +2 "$BASE/source.md" >> "$OUT"
```

### 验证方法

```bash
# 检查每编标题是否出现
grep -n '^# 第.*编' merged.md

# 合并后行数应接近各源文件行数之和（减去跳过的头部）
wc -l merged.md
```

## 覆盖率自验方法

PRD合并完成后，生成覆盖率自验报告验证所有功能点无遗漏。

### 核心方法：声明计数 vs grep匹配

每个PRD源文件头部通常会自声明功能点数量。用grep做交叉验证：

| 文件类型 | 功能点ID格式 | grep模式 | 注意事项 |
|---------|------------|----------|---------|
| 顺序编号 | `#1`, `#55`, `#768` | `^\| #\d+ ` | 最精确，1:1对应 |
| 块编号 | `FT-001`, `HYZX-STRAT-050` | `^\| \| (FT-\|GL-)` | 1个ID对应1-5个功能点，grep计数会偏低 |
| 前缀编号 | `YXZX-PRD-01-01-04` | `^\| YXZX-PRD-` | 前缀后数字组数不固定 |
| 表格编号 | `\| 1301 \| 功能名 \| ILF \|` | `^\| \d+ \|.*\| (ILF\|EI) \|` | 无前缀，靠数字列+类型列定位 |

### "块编号"陷阱

会员中心/策略中心等模块常使用"块编号"：一个功能ID（如 `HYZX-STRAT-050`）代表一组关联功能点（050-056），每个块内2-5个子功能点。grep统计独立ID数（如328个）远低于声明功能点数（如~790个），但**内容覆盖率仍是100%**——只是grep无法拆分块内子功能点。

**判定规则**：如果文件自声明数量 > grep独立ID数，且每个ID下确实有多行子功能点表，则覆盖率为100%，grep差异为格式原因。

### FPA类型统计（ILF/EI/EQ/EO）

对标注了FPA类型的文件，按类型统计分布：

```bash
echo -n "ILF: "; grep -cP 'ILF' source.md
echo -n "EI: ";  grep -cP 'EI' source.md  | grep -v 'ILF'
echo -n "EQ: ";  grep -cP 'EQ' source.md  | grep -v 'ILF'
echo -n "EO: ";  grep -cP 'EO' source.md  | grep -v 'ILF'
```

### 覆盖率报告结构

```markdown
## Sheet覆盖统计
| 子系统 | 文件 | 声明点数 | grep匹配 | 覆盖率 | 状态 |
## FPA类型分布
| 类型 | 数量 | 占比 | 说明 |
## 已知跳号/缺失分析
| 文件 | 范围 | 跳号 | 说明 |
## 综合结论
✅ 或 ⚠️ 判定，附具体差异数量和建议后续动作
```

真实案例输出参考本session的 `PRD覆盖率自验报告.md`（261行，含Sheet1/Sheet2双表统计、FPA分析、跳号清单）。

## 常见坑

1. **子Agent不能访问外部URL** — 如果合并需要来自外部URL的数据，先在主Agent中抓取并保存为本地文件，再传给子Agent
2. **字段覆盖验证** — 合并后行数应 ≥ 各源文件行数之和（减去跳过的头部）。如果合并后行数比任一源文件还少，说明发生了压缩。必须用 terminal cat 重做。
3. **版本标记** — 整合后标记为"V1.0 最终交付版"，源文件清单标注行数和来源
4. **子Agent压缩** — 永远不要委托子Agent做细节合并。子Agent适合做架构总览、状态映射、API定义等**新增的整合材料**，不适合做现有文档的机械拼接。机械拼接用 terminal cat。
5. **文件过大时的策略** — 如果合并后超过200KB，考虑分成"主文档（架构+整合）+ 附件A（小程序全文）+ 附件B（后管全文）"的三文件结构
6. **块编号不慌** — grep统计的独立ID数低于声明功能点数时，先检查是否为"块编号"（一个ID下含多个子功能点表行）。如果确认是块编号，覆盖率视为100%，在报告中备注差异原因即可。
