# PRD 市场调研总结 — 商用PRD vs AI原型PRD

> 调研时间：2026-06-24
> 调研范围：国内（知乎/明道/ProcessOn/飞书） + 国际（Atlassian/Aha.io/Figma/Formlabs/Notion）

## 核⼼发现

PRD分两种，目标读者和结构完全不同：

| 对比维度 | 商用PRD（给人看） | AI原型PRD（给机器看） |
|---------|----------------|-------------------|
| **目标读者** | 甲方/老板/开发/测试 | AI Agent / 原型生成器 |
| **核心问题** | "为什么要做这个？值不值得做？" | "每个按钮按下去应该发生什么？" |
| **黄金结构** | 背景→目标→范围→功能→非功能→接口→路线图 | 设计规范→信息架构→页面清单→功能点→数据模型→Mock数据→验收标准 |
| **需求粒度** | 模块级（"订单管理含增删改查"） | 按钮级（"审核按钮→弹出modal→选择通过/驳回→提交→刷新"） |
| **优先级标注** | MoSCoW（Must/Should/Could/Won't） | P0/P1/P2（影响原型生成行为不同） |
| **数据展示** | 概念性描述（"支持多种支付方式"） | 完整枚举 + 控件类型 + 校验规则 |
| **Mock数据** | 不写或示例 | 三组完整数据（正常/空/极限） |
| **非功能需求** | 必要（性能/安全/可用性SLA） | 不写（原型不涉及） |
| **接口规范** | 完整接口清单+参数说明 | 只需格式约定（影响Mock数据结构） |
| **竞品分析** | 必要章节 | 不写 |
| **风险路线图** | 必要章节 | 不写 |
| **文档控制** | 版本历史/变更记录/审批人 | 不写 |

## 市场PRD标准结构（综合各厂商）

综合国内外面向商业交付的PRD标准，典型结构为：

1. **文档控制** — 版本号/日期/修订记录/审批
2. **项目概述** — 背景/目标（量化KPI）/范围（本期vs下期）/干系人
3. **用户分析** — 角色定义/用户故事/使用场景
4. **功能需求** — 功能全景图（Feature Map）/模块规格/功能点表/业务规则/异常处理
5. **非功能需求** — 性能要求/安全要求/可用性要求
6. **数据模型** — ER图/数据字典/状态机
7. **界面交互** — 设计规范/页面清单/交互流程图
8. **接口规范** — 接口列表/请求响应格式/错误码
9. **实施规划** — 风险评估/分期交付/交付物清单
10. **附录** — 术语表/参考文档/竞品对标

## 关键洞察

1. **「PRD不是技术规格书」** — 明道创始人任向晖强调：PRD描述需求（WHAT），不是解决方案（HOW）。越俎代庖写数据表结构是常见误区。
2. **过度完整 vs 缺失细节** — 两者都是病。无经验者易写长篇大论（事无巨细），但有经验者易跳细节（字段不列全）。AI原型版倾向于后者。
3. **用户故事不可或缺** — 纯功能列表缺少代入感。好的PRD先用用户故事建立场景共识，再展开功能规格。但用户故事对AI原型生成无直接价值。
4. **命名约定至关重要** — 术语一旦确定，整个PRD + 原型 + 开发必须统一使用，不可随意变更。
5. **迭代优于完整** — PRD第一版不需要绝对完整。敏捷开发模式下，持续迭代PRD比追求首版完美更重要。
6. **MoSCoW是工业标准** — Must/Should/Could/Won't是比P0-P3更广泛接受的优先级标注方式，适合跨团队沟通。P0/P1/P2更适合AI的执行语境。

## 对PRD技能的影响

- **VERSION A（商用交付版）** 遵循上述第4点中的10章结构 + MoSCoW + 文档控制 + 竞品分析 + 路线图
- **VERSION B（AI原型生成版）** 采用P0/P1/P2 + 按钮级粒度 + 完整枚举 + 三组Mock数据 + 边界条件表
- 两者共享Ch1（设计规范）/ Ch2（信息架构）/ Ch5-Ch7（页面+功能+数据），但表达深度不同
